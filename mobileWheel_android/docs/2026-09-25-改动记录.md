## 3. 改动详情

### 3.1 横屏锁定与翻转不重建

`AndroidManifest.xml` 的 MainActivity 节点：

```xml
android:screenOrientation="sensorLandscape"
android:configChanges="orientation|screenSize|smallestScreenSize|screenLayout|keyboardHidden"
```

`configChanges` 让翻转只回调 `onConfigurationChanged`，不重建 Activity，监测过程不中断。

### 3.2 布局与主题

- `activity_main.xml`：根 `LinearLayout`（horizontal，`padding=16dp`，`fitsSystemWindows="true"`，浅色背景）。左侧 `layout_weight=1.4` 放标题「横向水平仪」+ 副标题 + `LevelView`；右侧 `layout_weight=1` 放 CardView「检测数据」，含传感器状态 / 横屏方向 / 横向倾角（24sp）/ 倾斜方向，下方是「开始监测」「停止监测」「开启蓝牙广播」「关闭蓝牙广播」按钮。
- 数据卡片中 4 个标签用 `wrap_content + minWidth=104dp + maxLines=1`，避免「传感器状态:」换行。
- 主题改为 `Theme.MaterialComponents.DayNight.NoActionBar`（`values/themes.xml`、`values-night/themes.xml`）：原 DarkActionBar 的紫色标题栏会盖住横屏内容；配合 `fitsSystemWindows` 处理 edge-to-edge 下的状态栏内边距。

### 3.3 显示：竖直指针 + 地平线（LevelView.kt）

- 底盘：圆角矩形（`pad=6dp`，圆角 `14dp`，色 `#263238`）。
- 背景组：`clipPath` 圆角矩形 → `canvas.rotate(angle, cx, cy)` 反向旋转 → 画地面矩形（`#33691E`，水平时 `#2E7D32`）+ 地平线（`#ECEFF1`）。因此地平线始终与真实地平线平行。
- 前景组：固定竖直向上的三角指针（中心 + 底部小圆），不随倾角摆动。
- 水平判定阈值 `LEVEL_TOLERANCE_DEG = 0.5f`。
- 对外接口 `update(tilt: Float, active: Boolean)`；文案：未开始 / 水平 / 向左倾斜 / 向右倾斜。

### 3.4 倾角计算与屏幕方向重映射（MainActivity.kt）

- 传感器：优先 `TYPE_GRAVITY`；不可用时退回 `TYPE_ACCELEROMETER` 并做低通滤波 `LOW_PASS_ALPHA = 0.15f`。采样 `SENSOR_DELAY_GAME`。
- 设备坐标 → 屏幕坐标重映射（等价 `remapCoordinateSystem` 的轴选择）：

| `Display.getRotation()` | screenX | screenY |
| --- | --- | --- |
| `ROTATION_90` | `-gravity[1]` | `gravity[0]` |
| `ROTATION_180` | `-gravity[0]` | `-gravity[1]` |
| `ROTATION_270` | `gravity[1]` | `-gravity[0]` |
| 其它 | `gravity[0]` | `gravity[1]` |

依据：Android 约定「设备相对自然方向逆时针旋转 90° 时为 `ROTATION_90`」，此时屏幕「上」= 设备 +X、屏幕「右」= 设备 -Y。

- 横向倾角（对俯仰不敏感的 roll）：

```
horizontal = sqrt(screenY² + gravity[2]²)
angle = toDegrees(atan2(screenX, horizontal))
```

- 方向语义：`angle > 0` ⇔ 屏幕左侧偏低 ⇒「向左倾斜」；`angle < 0` ⇒「向右倾斜」；`|angle| <= 0.5°` ⇒「水平」。
- **已修复的 bug**：初版重映射为 `ROTATION_90 → screenX = gravity[1]`，整体差 180°，导致实测左右文案相反；上表为修正后的符号。

### 3.5 显示方向提示

`updateLandscapeDirection()`：`ROTATION_90` →「横屏 · 正向」，`ROTATION_270` →「横屏 · 反向」，`ROTATION_0/180` → 竖屏，其余 → 未知。`onConfigurationChanged` 中刷新。

### 3.6 蓝牙：TiltBleServer.kt（BLE 外设 / GATT Server）

- 手机端做 GATT Server + `BluetoothLeAdvertiser` 广播，客户端订阅后按需 Notify。
- 启动条件：`adapter.isEnabled` 且 `isMultipleAdvertisementSupported`；失败时状态栏给出原因文案。
- 连接建立后主动停止广播；断开后自动恢复广播。
- 订阅（CCCD 写 `ENABLE_NOTIFICATION_VALUE`）成功时补发最近一次读数。
- 数据发送在 `MainActivity.sendTiltOverBle()`，按 `BLE_SEND_INTERVAL_MS = 50L`（约 20Hz）限流，避免传感器满速刷 BLE。
- 权限：Android 12+ 需要运行时授权 `BLUETOOTH_ADVERTISE` / `BLUETOOTH_CONNECT`；`AndroidManifest.xml` 中 ≤30 用旧权限（`BLUETOOTH`/`BLUETOOTH_ADMIN` + `maxSdkVersion=30`），31+ 用新权限，并声明 `android.hardware.bluetooth_le`。

### 3.7 广播失败降级重试（未提交）

**问题**：实测日志出现 `startAdvertising failed: 3`（`ADVERTISE_FAILED_INTERNAL_ERROR`），广播根本没起来，原代码失败后不重试，因此 Windows 侧搜不到、连不上。

**修复**：新增 `ADVERTISE_CONFIGS` 降级阶梯，失败自动换下一组重试，并把错误码与所用参数写入日志：

| 次序 | 模式 | 扫描响应带设备名 |
| --- | --- | --- |
| 1 | `ADVERTISE_MODE_LOW_LATENCY` | 是 |
| 2 | `ADVERTISE_MODE_BALANCED` | 是 |
| 3 | `ADVERTISE_MODE_BALANCED` | 否 |
| 4 | `ADVERTISE_MODE_LOW_POWER` | 否 |

另补日志：`onServiceAdded`、`onConnectionStateChange`、`startAdvertising (attempt/config/maxDataLen)`、`advertising started`。广播链路在 `start()` 时把 `advertiseAttempt` 重置为 0，重连复播时沿用已生效的那一组。

## 4. BLE 协议（给 Windows 客户端的对接说明）

| 项 | 值 |
| --- | --- |
| Service UUID | `0000a100-0000-1000-8000-00805f9b34fb` |
| 数据特征值 UUID | `0000a101-0000-1000-8000-00805f9b34fb`（Notify + Read） |
| CCCD | `00002902-0000-1000-8000-00805f9b34fb` |
| 设备名 | 取自系统蓝牙名，放在扫描响应中（App 无法自定义） |
| 广播包内容 | 仅 Service UUID（+ 自动 flags），`setConnectable(true)`，避免超过 31 字节上限 |

数据格式（每次 Notify 一行 JSON）：

```json
{"angle":-3.3,"direction":"向右倾斜","rotation":270,"ts":1790314159000}
```

- `angle`：横向倾角，正 = 左侧偏低（向左倾斜）
- `direction`：中文方向文案
- `rotation`：`Display.getRotation()`，横屏下为 90 或 270
- `ts`：毫秒时间戳

注意事项：

- 需要先点「开始监测」，否则没有数据源，不会推送。
- JSON 约 60 字节，超过默认 ATT MTU 23 的 20 字节载荷，客户端需协商较大 MTU（Win10/11 通常自动协商到 512）。
- 连上后设备停止广播，扫描列表里“消失”属正常；断开后自动重新广播。

## 6. 未解决问题与备选路线

**未解决**：Windows 侧连接仍失败，提示「请尝试重新连接」。已排除 Android 侧广播问题（上面第 3、4 条证据），问题在 Windows 端的连接入口/配对环节。

判断与备选：

1. **若是在 Windows「设置 → 添加蓝牙设备」里连** —— 该入口只对经典蓝牙设备和 BLE HID（键鼠/手柄）友好，对普通自定义 BLE GATT 外设只会尝试配对，失败属预期。BLE GATT 外设的正确用法是客户端扫描 Service UUID 后直连订阅，**全程不需要配对**；且 Android 的 BLE 外设配对由系统协议栈处理，App 层没有 API 可以干预。
2. **改成 BLE HID 手柄**：在 GATT Server 注册标准 HID 服务 `00001812-0000-1000-8000-00805f9b34fb`（Report Map / HID Information / Report 等特征值），广播里把 Appearance 设为手柄，Windows 会像 BLE 手柄一样在系统界面里配对成功。代价：数据只能走二进制 HID 报告，JSON 行协议作废，客户端要改用 hidapi 读；MIUI 对 App 注册 HID 服务可能有额外限制，需实测。
3. **改成经典蓝牙 HID**（`BluetoothHidDevice`，API 28+）：Windows 配对稳定，但同样只剩 HID 报告通道，且要求 host 先 bond。
4. **改成经典蓝牙 SPP 串口**：手机开 RFCOMM 服务，Windows 配对后建 COM 口，客户端串口读 JSON 行——**能保留现有协议**，代价是要在 Windows 里手动加一次 COM 口，且手机需临时开启经典蓝牙可见性。

## 8. 局域网（TCP）通道（BLE 路线的替代方案）

### 8.1 背景

第 6 节的 BLE 路线被 Windows 侧驱动阻断（Intel 无线蓝牙驱动 21.80.0.3 与 Windows 11 build 26200 不匹配，连接 338ms 后被 `HCI_ERR_CONN_FAILED_ESTABLISHMENT (0x3e)` 拆链，无管理员权限改驱动）。因此**新增局域网 TCP 通道**，BLE 代码原样保留、不删不改，两条通道并行发送，客户端连上哪条都能收数据。

### 8.2 协议

| 项 | 值 |
| --- | --- |
| 传输 | TCP，**手机为服务端**，Windows 为客户端 |
| 端口 | `11223` |
| 分帧 | 每行一条 JSON，`\n` 结尾 |
| 数据 | `{"angle":-3.3,"direction":"向右倾斜","rotation":270,"ts":1790314159000}`（与 BLE 通道完全一致） |
| 限流 | 与蓝牙共用 `SEND_INTERVAL_MS = 50L`（约 20Hz） |

### 8.3 Android 改动

- **`TiltNetServer.kt`（新增）**：`ServerSocket` 监听 11223，接受多个客户端；接口与 `TiltBleServer` 对齐（`start()/stop()/send()/isReady/onStatusChanged`），`MainActivity` 无需区分通道。`localIpAddress()` 取本机局域网 IPv4 用于界面显示。
- **`MainActivity.kt`**：`sendTiltOverBle()` 改名 `sendTilt()`，同时向两个通道发送（原限流常量改名 `SEND_INTERVAL_MS`）；新增 `setupLan()/startLan()/stopLan()` 与按钮联动；`onDestroy` 释放监听。
- **`AndroidManifest.xml`**：新增 `android.permission.INTERNET`。
- **`activity_main.xml`**：数据卡片新增「局域网:」状态行（显示 `监听中 IP:端口` / `已连接: 客户端`）；「开启蓝牙广播」「开启局域网」两个按钮**并排一行**，并把卡片内各行间距由 10dp 压到 2dp——否则横屏高度不够，卡片下方状态行会被裁掉看不见。

### 8.4 关键 bug 与修复：主线程写 socket 导致进程崩溃

**现象**：客户端一连上，App 立刻退出，客户端收到 EOF；logcat 里是

```
FATAL EXCEPTION: main
android.os.NetworkOnMainThreadException
  at TiltNetServer$ClientWriter.writeLine(TiltNetServer.kt:156)
  at TiltNetServer.send(TiltNetServer.kt:90)
  at MainActivity.sendTilt(MainActivity.kt:307)
  at MainActivity.updateLevel(MainActivity.kt:286)   ← onSensorChanged 在主线程
```

**原因**：传感器回调在主线程，`send()` 直接 `flush()` 触发了 Android 的 StrictMode 网络限制。

**修复**：`send()` 只把数据投进容量 1 的 `LinkedBlockingQueue`（满则丢旧帧，只保留最新值），由 `TiltNetServer-Writer` 线程统一串行写 socket；新客户端接入时的补发也走同一队列。

```kotlin
fun send(line: String) {
    lastLine = line
    if (!running || clients.isEmpty()) return
    if (!outbox.offer(line)) { outbox.poll(); outbox.offer(line) }
}
```

### 8.5 Windows 改动

- **`Services/TiltNetClient.cs`（新增）**：`TcpClient` 连接后按行读取，字节流喂给既有的 `TiltFrameParser` → `TiltReading`；对外事件与 `TiltBleClient` 一致（`Log` / `ReadingReceived` / `ConnectionStateChanged`），`ConnectAsync(host, port)` 10s 超时。
- **`ViewModels/MainWindowViewModel.cs`**：新增 `ServerEndpoint`（`IP:端口`，`ParseEndpoint` 校验）与 `ConnectLanCommand` / `DisconnectLanCommand`；连接状态事件按传输区分（`OnConnectionStateChanged(connected, isBle)`），只有 BLE 断线才走「自动重新扫描」，局域网断线由用户手动重连；状态栏显示 `已连接 · <地址>`。
- **`Views/MainWindow.axaml`**：左列改为「BLE 设备列表 + 局域网连接」两卡片，局域网卡片含 `IP:端口` 输入框与连接/断开按钮。

### 8.7 使用步骤与注意事项

1. 手机与电脑连同一局域网（本例 192.168.100.0/24）。
2. 手机 App：点「开启局域网」→ 点「开始监测」，记下状态行里的 `IP:端口`。
3. Windows 端：在「局域网连接」输入框填入该地址 → 点「连接」。
4. 注意：**手机 App 必须保持在前台**。实测出现过一次 10s 连接超时，当时手机处于闲置（进程被 MIUI 冻结），唤醒后再连立刻成功；若频繁复现，需给本应用关闭省电优化 / 允许后台运行。→ 该问题已由第 9 节的「后台保活」解决。
5. 多客户端可同时连接，发送端为单写线程，客户端读得慢时会丢弃旧帧只发最新值。

### 9.2 Windows 表盘：固定地平线 + 旋转指针

`Controls/LevelGauge.cs` 由「刻度盘 + 气泡」改为人工地平仪样式（与手机端 `LevelView` 同构）：

- 背景（固定不动）：圆角底盘 `#263238` + 地平线以下填充地面（水平 `#2E7D32` / 倾斜 `#33691E`）+ 白色水平线 `#ECEFF1`；
- 前景：三角指针 + 中心点，按 `-angle` 旋转（`Matrix.CreateRotation`，正角为顺时针），水平时绿色 `#66BB6A`、倾斜时橙色 `#FFA726`；
- 指针超出 ±90° 时截断。

角度符号与手机端一致（`angle > 0` = 屏幕左侧偏低 = 向左倾斜）。手机端是「指针固定、地平线顺时针转 angle」，等价于「地平线固定、指针逆时针转 angle」，因此电脑端指针按 `-angle` 旋转，两侧看到的指针与地平线的相对方向完全一致。

**Windows 端**：`MainWindowViewModel` 增加后台重连循环：

- 记住最近一次成功的 `IP:端口`（`_lastEndpoint`）；意外断线且「断线后自动重连」勾选时，每 3s 重试一次，直到连上或用户主动连接/断开/取消勾选；

### 9.7 响应速度优化

**问题**：Windows 端显示相对手机倾斜有明显延迟。

**定位**：逐段排查延迟来源——

1. 手机发送限流 `SEND_INTERVAL_MS = 50L`（理论 20Hz）：实测帧间隔约 52ms、19.3Hz，与限流值完全吻合 → **主要瓶颈**；
2. 手机传感器采样 `SENSOR_DELAY_GAME`（约 20ms / 50Hz）：次要；
3. Windows 侧：`TiltNetClient` 已设 `NoDelay`，`ReadAsync` 一收到字节就解析并逐帧上报，无批处理或缓冲；`Dispatcher.UIThread.Post` 逐帧派发在几十 Hz 下不构成瓶颈；`TiltFrameParser` 的 `List<byte>` 每帧搬移约 60 字节，量级可忽略。

**改动**：

- `SEND_INTERVAL_MS` `50L → 16L`（约 60Hz，与显示刷新率对齐）。此时传感器每次回调（约 20ms）都能发出，限流不再丢帧；
- `LevelGauge` 缓存指针 `StreamGeometry`（尺寸不变时复用），去掉每帧重建几何的开销。

**验证**：用独立 TCP 客户端统计 6s 窗口内的帧间隔——

| 版本 | 帧数 / 6s | 平均间隔 | 频率 |
| --- | --- | --- | --- |
| 优化前 | 116 | ≈52ms | 19.3Hz |
| 优化后 | 283 | 21.3ms | 47Hz |

**剩余可优化项（未做，按需）**：把传感器改为 `SENSOR_DELAY_FASTEST` 可再省约 5–10ms 的采样量化延迟，代价是回调频率翻倍、更费电。当前端到端典型延迟约 27ms（采样约 10ms + 网络 <1ms + 显示刷新 ≤16ms），已在人眼不易察觉的范围。

## 10. 电脑端模拟方向盘（虚拟 Xbox 360 手柄）

### 10.1 目标与方案

让游戏把电脑端识别成**方向盘设备**，方向盘转角等于手机倾角。

选择 **ViGEmBus + `Nefarius.ViGEm.Client`** 模拟一个虚拟 Xbox 360 手柄，用**左摇杆 X 轴**当方向盘转角轴：

| 优点 | 说明 |
| --- | --- |
| 被绝大多数游戏识别 | XInput 手柄是通用输入，游戏里把「转向 / Steering」绑到「左摇杆 X」即可，不需要每个游戏单独适配 |
| 无需管理员权限 | ViGEmBus 是内核驱动但已安装，用户态调用普通权限即可 |
| 不动现有协议 | 手机端一行代码没改，仍是局域网 JSON |

未选 vJoy：需手动装驱动 + 逐个游戏配置，且项目已自带 ViGEmBus 环境。

### 10.2 映射关系

```
axis = round(-clamp(angle, -90, 90) / 90 * 32767)     // short，左摇杆 X
```

- 满舵角 **±90°**，与手机倾角 **1:1**（`FullLockAngle = 90`）；
- **负号的含义**：`angle > 0` 表示手机**向左**倾斜（左侧偏低），相当于把方向盘**左打**，而 XInput 左摇杆 X 轴**向左为负**，所以取负；
- 超出 ±90° 按满舵截断，不溢出 `short`。

| 手机倾角 | 左摇杆 X | 方向盘 |
| --- | --- | --- |
| 0° | 0 | 正中 |
| +45° | -16384 | 左半舵 |
| +90° | -32767 | 左满舵 |
| -90° | +32767 | 右满舵 |

### 10.3 改动清单

| 文件 | 改动 |
| --- | --- |
| `mobileWheel_win.csproj` | 新增 `Nefarius.ViGEm.Client` 1.21.256 |
| `Services/TiltGamepad.cs` | **新增**：虚拟手柄的创建 / 拔出 / 轴写入 / 数据看门狗 |
| `ViewModels/MainWindowViewModel.cs` | 新增 `GamepadEnabled`、`GamepadStatus`；读数到达时在数据线程直接喂手柄；断线时回中；`Dispose` 释放 |
| `Views/MainWindow.axaml` | 局域网卡片新增「模拟方向盘（虚拟 Xbox 360 手柄）」勾选框与状态文本 |

要点：

- **native DLL 不用手动放**：`Nefarius.ViGEm.Client` 用 Fody Costura 把 `vigemclient.dll`（x86/x64）内嵌在托管 DLL 里，运行时自动解包，所以 `mobileWheel_win` 输出目录里看不到它也能工作。
- **数据线程直接写手柄**：`OnReadingReceived` 里在 `Dispatcher.UIThread.Post` **之前**调用 `_gamepad.Update(reading.Angle)`，不为方向盘多走一趟 UI 线程。
- **只在勾选时映射**：`GamepadEnabled` 关闭时不碰手柄，避免未使用时的额外开销。
- **数据看门狗**：500ms 收不到新数据就自动回中，防止「停止监测」后方向盘卡在满舵。
- **带锁串行**：`Update`（数据线程）、`Reset`（UI 线程）、看门狗（Timer 线程）都会写手柄，用同一把锁串行；同时记住上次写入值，值没变就不重复下发。

### 10.4 踩到的坑：ViGEmBus 新建手柄的摇杆初始值不是 0

**现象**：刚创建虚拟手柄、还没有任何倾角数据时，用 XInput 读到左摇杆 X 是 **-3356**（约 10% 左偏），而不是 0。

**定位**（`ResetReport()` / `SubmitReport()` 后 XInput 的 `dwPacketNumber` 始终停在 1，说明报告根本没下发）：

- ViGEmBus 新建虚拟手柄的摇杆初值并非 0；
- `ViGEm.NET` 对**与上次完全相同的报告不会重复下发**，而托管侧的报告初值是全 0，因此 `ResetReport()`、`SetAxisValue(LX, 0)` 这类「写 0」的调用都被静默跳过，驱动里的 -3356 就一直留着。
- 后果：如果手机一开始就是水平的（`angle` 恰为 0），方向盘会一直偏左 10%，直到第一次非零读数才被纠正。

**修复**（`TiltGamepad.Connect()`）：插入后先写一个非 0 值再写回 0，强制产生两次真实下发；同时把内部记录的上次值置为 0。

```csharp
_pad.SetAxisValue(Xbox360Axis.LeftThumbX, 1);
_pad.SetAxisValue(Xbox360Axis.LeftThumbX, 0);
_lastAxis = 0;
```

## 11. 手机端左右竖向滑动条模拟 LT / RT 扳机

### 11.1 需求与布局

手机端最左、最右各加一个**竖向滑动条**，分别模拟 Xbox 360 手柄的 **LT / RT 扳机**；数据面板与水平仪面板整体移到中间，并适当缩小水平仪。

`activity_main.xml` 重写为「左滑条 | 中间（水平仪 + 数据） | 右滑条」三栏：

| 区域 | 宽度 | 内容 |
| --- | --- | --- |
| 左列 | 72dp 固定 | `LT` 标签 + `seekLt` 竖向滑条 + 数值 `tvLtValue` |
| 中间 | `0dp` + weight 1 | 左半：水平仪标题 + `LevelView`（**240dp × 240dp**，`layout_gravity="center"`，由原 1:1 自适应缩小并居中）；右半：原数据卡片 + 3 个按钮 |
| 右列 | 72dp 固定 | `RT` 标签 + `seekRt` 竖向滑条 + 数值 `tvRtValue` |

两个滑条都是 `android:max="255"`、`layout_height="0dp"` + `weight=1`（长边）、`layout_width="match_parent"`（宽 72dp 就是条的粗细）。

### 11.2 `VerticalSeekBar`：为什么不用 `android:rotation="270"`

新增 `VerticalSeekBar.kt`（继承 `AppCompatSeekBar`）。用 `rotation` 旋转控件时，布局系统仍按原方向测量，要手工做宽高互换补偿，而且触摸坐标不会跟着旋转、点击位置会错位。这里改为标准做法：

- `onMeasure`：先用互换后的 spec 调 `super`，再 `setMeasuredDimension(measuredHeight, measuredWidth)` 把宽高对调；
- `onSizeChanged(w, h, …)`：转发 `super.onSizeChanged(h, w, …)`；
- `onDraw`：`canvas.rotate(-90f)` + `canvas.translate(-height, 0f)`，即把横条转成竖条；
- `onTouchEvent`：自己把 `event.y` 换算成进度（`ACTION_MOVE` / `ACTION_UP` 都更新），**顶部为满值**（滑到最上面 = 扳机按到底）；`ACTION_UP` / `ACTION_CANCEL` 后用 120ms 动画回到 0（见 11.8）；
- `setProgress` 后补调 `onSizeChanged(width, height, 0, 0)`，否则代码改进度时绘制不会立即刷新。

### 11.3 协议扩展：新增 `lt` / `rt`

手机端 `sendTilt()` 的 JSON 增加 `lt` / `rt`（0..255，取两个滑条的 `progress`）：

```
{"angle":-0.6,"direction":"向右倾斜","rotation":3,"lt":127,"rt":0,"ts":1790348452823}
```

- 仍在 `sendTilt()` 里保留 16ms 限流；滑块变化时走 `force = true` 立即补发一帧。加这个是因为**手机静止时重力传感器可能长时间不回调**（实测出现过 29s 空档），只靠周期性发送会让扳机变化迟迟传不过去；`sendTriggerNow()` 用最近一次的 `lastAngle` / `lastDirection` 组帧。
- Windows 端 `TiltReading` 扩展为 `(Angle, Direction, Rotation, Timestamp, LeftTrigger, RightTrigger)`，`lt` / `rt` 为可选字段（旧版手机端不发时按 0），读取后夹到 0..255。

### 11.4 Windows 侧：扳机写入虚拟手柄

`TiltGamepad` 由「只写一个轴」扩展为「轴 + 两个扳机」：

- `Update(double angle, int leftTrigger, int rightTrigger)` → `Write(ToAxis(angle), ToTrigger(lt), ToTrigger(rt))`；
- `ToTrigger(v) => (byte)Math.Clamp(v, 0, 255)`；
- `Write` 内部按「值没变不重复下发」对三路各自判断（`Xbox360Axis.LeftThumbX`、`Xbox360Slider.LeftTrigger`、`Xbox360Slider.RightTrigger`）；
- `Connect()` 的强制首次下发扩到三路（仍先写 1 再写 0），`Reset()` / 看门狗超时 / 断线统一 `Write(0, 0, 0)`（方向盘回中 + 扳机松开）。

`MainWindowViewModel.OnReadingReceived` 在 `Dispatcher.UIThread.Post` 之前调用
`if (GamepadEnabled) _gamepad.Update(reading.Angle, reading.LeftTrigger, reading.RightTrigger);`，数据线程直喂，不为扳机多走一趟 UI 线程。

### 11.5 踩到的坑：`Xbox360Slider.LeftTrigger` 不是 `LeftTriggerSlider`

编译报 **CS0122「…不可访问，因为它具有一定的保护级别」**（6 处）。

原因：误把 `LeftTriggerSlider` 当成了「扳机字段名」，它其实是 `Xbox360Slider` 里一个 **private 的嵌套类型**（`RightTriggerSlider` 同理）；真正可用的 **public static 字段**名是 `LeftTrigger` / `RightTrigger`。用反射 dump `Public,Static` 字段确认后把这 6 处全部替换即通过（0 警告 0 错误）。

### 11.7 使用说明与注意事项

- 手机端：最左滑条 = LT，最右滑条 = RT，**往上滑是按下扳机**（顶部 = 255），**松手立刻回 0**（与真扳机一致）；滑条下方的数字就是当前值。
- 扳机只在「开始监测」后才会发送（与倾角数据同一条件）。
- Windows 端：勾选「模拟方向盘（虚拟 Xbox 360 手柄）」后，游戏里把油门/刹车绑到 **LT / RT**（左/右扳机）即可；方向盘仍是**左摇杆 X 轴**。
- 数据看门狗 500ms 生效：停止监测或断网后方向盘回中、扳机松开，游戏里不会卡在满油门。
- 若希望滑条更细腻/更粗，改左、右两列的 `layout_width`（72dp）；若滑条与水平仪想再换宽度，中间栏是两个 `weight=1` 的等分，改权重即可。

### 11.8 松手后 LT / RT 归零（扳机回弹）

**需求**：滑条是「扳机」，按下去才有值，手指离开就该像真扳机一样弹回 0，不能停在按下位置。

**实现**

1. `VerticalSeekBar`：`ACTION_UP` / `ACTION_CANCEL` 后调 `animateBackToZero()` —— 用 `ValueAnimator` 在 **120ms** 内把 `progress` 从当前值插值到 0（`ACTION_DOWN` 时先 `cancel()` 上一次动画，避免抖动；`onDetachedFromWindow` 也取消）。
2. `MainActivity.triggerListener`：发送条件从「只有用户拖动（`fromUser`）才补发」改为**只要 `progress` 变化就补发**。因为回弹动画是代码改进度（`fromUser = false`），按旧写法电脑端收不到「松开」这一帧，扳机会一直停在按下的值。现在动画过程中的每一帧都会发出去，电脑端看到的扳机是平滑落下而不是瞬间跳变。

电脑端不用改：`TiltGamepad` 已经按帧写入 `Xbox360Slider.LeftTrigger` / `RightTrigger`，收到 `lt=0` 就把扳机松开。

**验证**（真机 + 真 App + XInput 回读，50ms 采样）

| 动作 | 虚拟手柄读数序列（与按下进度同步） |
| --- | --- |
| LT 按住上拖 600ms 后松手 | 83 → 97 → 109 → 121 → 135 → 144 → 156 → 167 → **179**（松手）→ 58 → 0，约 200ms 内归零 |
| LT 点靠近顶部后松手 | 185（松手）→ 79 → 0，约 130ms 内归零 |
| RT 按住上拖 600ms 后松手 | 82 → 92 → … → 187 → 58 → 0 |
| RT 点靠近顶部后松手 | 118 → 4 → 0 |

按住期间数值跟随手指连续变化（不会被 500ms 看门狗误判为超时，因为数据一直在流）；松手后手机端数值标签也立刻显示 `0`（`uiautomator dump` 确认 `tvLtValue=0`、`tvRtValue=0`）。

### 14.2 倾角 → 摇杆映射（`Services/TiltGamepad.cs`）

`FullLockAngle` 由 `90` 改为 `60`，新增 `DeadZoneAngle = 5`，并把 `ToRatio` / `ToAxis` 提为 `public static`（ViewModel 要拿它做显示）：

```csharp
public static double ToRatio(double angle)
{
    var magnitude = Math.Abs(angle);
    if (magnitude <= DeadZoneAngle) return 0d;          // ±5° 死区：视为水平

    var span = FullLockAngle - DeadZoneAngle;           // 55°
    var ratio = Math.Min(magnitude - DeadZoneAngle, span) / span;
    return angle < 0 ? ratio : -ratio;                  // 向左倾斜 → 负值（左打）
}
```

直接复用大窗口的 `Controls/LevelGauge`（70×70），绑定新的派生属性 `SteeringPointerAngle`，下方保留一枚 `SteeringText` 小字（`居中` / `左 90%`）：

```csharp
/// <summary>方向盘指示箭头角度：0 居中，向左打方向为正值（箭头向左偏），满舵 ±60°</summary>
public double SteeringPointerAngle => -SteeringRatio * TiltGamepad.FullLockAngle;
```

`LevelGauge` 内部是 `Matrix.CreateRotation(-Angle, center)`，所以 `Angle > 0` 时箭头向左偏；而 `ToRatio` 对「向左倾斜（倾角为正）」返回负值，乘上负号后 `SteeringPointerAngle` 为正 → **向左倾斜箭头向左偏**，与大窗口的方向语义一致。箭头偏转幅度用的是**映射后的舵量**（±5° 死区内为 0、满舵 ±60°），而不是原始倾角，这样它表达的就是真正的「模拟量」。

### 15.4 坑：小窗里旋转 `ProgressBar` 会被拉伸到整窗高度

第 14 节里 LT / RT 竖条的做法是「固定尺寸 `Panel` 里套一个横 `ProgressBar`，再 `RotateTransform Angle="-90"`」。大窗口里一直正常，但把窗口缩到 `205×120` 后，两条竖条**从上到下贯穿了整个窗口**：像素测量显示轨道色 `#334155` 从 `y=0` 连续到 `y=179`（正好是客户区全高 180 物理像素），而声明的是 `9×86` 逻辑（应为 129 物理像素）；UIA 对两条 `ProgressBar` 上报的都是 `15×300` 物理，与两种预期尺寸都不符。

同一份写法在大窗口没问题、小窗就被拉伸，说明旋转后的 `ProgressBar` 在小窗里的盒模型尺寸不可控，没有再继续排查模板，直接换成**确定性的 `Border` 方案**：

```xml
<Border Width="9" Height="86" Background="#334155" CornerRadius="3" ClipToBounds="True">
  <Border VerticalAlignment="Bottom" Height="{Binding LeftTriggerBarHeight}" Background="#22D3EE" />
</Border>
```

外层 `Border` 当轨道（固定 9×86、圆角、`ClipToBounds` 把填充裁在圆角内），内层 `Border` 贴底、高度按比例绑定；VM 补两个派生属性，`TriggerBarHeight = 86` 与 XAML 里的轨道高度一一对应：

```csharp
public const double TriggerBarHeight = 86;
public double LeftTriggerBarHeight  => LeftTrigger  / 255d * TriggerBarHeight;
public double RightTriggerBarHeight => RightTrigger / 255d * TriggerBarHeight;
```

大窗口那两条竖条（`MainWindow.axaml`）尺寸没变、没出问题，保持原样不动，因此 `LeftTriggerValue` / `RightTriggerValue` 仍然保留。

### 16.2 安卓：绕开 `AbsSeekBar` 的排版，改成完全自绘轨道

先说明取舍：字面「可触控面积 3 倍」意味着把 seekbar 视图宽度从 55dp 加到 165dp。但左右两列各只有 72dp，加宽之后中间列会从约 486dp 被挤到 262dp，而中间还要放 240dp 的水平仪 + 数据卡，放不下；而且用户抱怨的是「bar 条本身横向太窄」，所以按**轨道粗细 2dp → 6dp（3 倍）** 实现，视图宽度（触摸命中带）不变。

**第一条路：直接改 `progressDrawable` 的固有高度。** 把图层/形状的高度从 2dp 改成 6dp，实测轨道确实从 6 物理像素变成 17 物理像素（≈3 倍 ✓），但**轨道中心从 x=144.5 漂到 x=136，而滑块中心仍在 x=145，偏心约 9px（3dp）**，竖条贴在滑块左半边。原因：`AbsSeekBar` 是按 `progressDrawable` 的**固有高度**去算轨道相对滑块的对齐位置，改固有高度就等于改了对齐，两者不能兼顾。

**第二条路：保留 2dp 的 `<size>`、改用 `<stroke android:width="4dp">` 撑开。** 期望「可见粗细 = 2dp + 4dp = 6dp」且对齐位置不变。实测**同心问题确实解决**（轨道中心 x=144.5、滑块中心 x=145 ✓），但粗细失控：**48 物理像素 ≈ 17dp**（约 8 倍，比滑块还粗，滑块被埋进轨道里）；而且 `<clip>`（`ClipDrawable`）的裁剪范围跟着自身 bounds 走，进度那一层有被裁回 2dp 的风险。这条路要在 `AbsSeekBar` + `LayerDrawable` + `ShapeDrawable` 三者的排版细节里试参数，不可控，放弃。

**最终方案：完全自绘。** 布局里把两个 seekbar 的 `android:progressDrawable` 设成 `@android:color/transparent`（留一个透明 drawable，避免 `AbsSeekBar` 内部状态为空），只让 `super.onDraw` 负责画滑块；轨道与进度全部在 `VerticalSeekBar.drawTrack()` 里画：

```kotlin
/** 轨道横向粗细：6dp（改造前是 2dp 的 drawable，约 3 倍） */
private val trackThickness = 6f * resources.displayMetrics.density

override fun onDraw(canvas: Canvas) {
    canvas.save()
    canvas.rotate(-90f)
    canvas.translate(-height.toFloat(), 0f)
    drawTrack(canvas)
    super.onDraw(canvas)
    canvas.restore()
}

private fun drawTrack(canvas: Canvas) {
    val thumbBounds = thumb?.bounds ?: return
    if (thumbBounds.isEmpty) return

    val centerY = (thumbBounds.top + thumbBounds.bottom) / 2f  // 取滑块中心 → 天然同心
    val half = trackThickness / 2f
    val length = height.toFloat()                              // 与 progressFromY 的触摸换算一致
    val level = if (max > 0) progress.toFloat() / max else 0f

    trackRect.set(0f, centerY - half, length, centerY + half)
    canvas.drawRoundRect(trackRect, half, half, trackPaint)

    if (level > 0f) {
        trackRect.set(0f, centerY - half, length * level, centerY + half)
        canvas.drawRoundRect(trackRect, half, half, progressPaint)
    }
}
```

要点：

- 旋转后 canvas 的 x 轴 = 屏幕上「自下而上」，y 轴 = 屏幕上「从左到右」；横向中心直接取**滑块 bounds 的中心**，所以同心是构造保证的，不再依赖框架的排版规则；
- 长度用 `height`，与 `progressFromY()` 的触摸换算（顶部为满值、整条高度对应 0..max）完全一致，视觉与可拖动范围对齐；
- 配色沿用原来的灰 `#D7D7D7` / 青 `teal_200`，圆角取半厚，两端是半圆；
- 中间稿新建的 `res/drawable/vertical_seek_progress.xml` 已删除。

## 19. 电脑端扫描局域网设备；输入框只填 IP；可用角度改为 0°~60°

### 19.1 需求拆解

1. 客户端能扫描局域网里开放 **11223** 端口的主机，扫到的设备列出来，点一下就能连；
2. 连接输入框只需要填 **IP**，端口自动补 `11223`；
3. 「可用角度」调整为 **0°~60°**（原来 ±5° 以内视为水平，有效区间是 5°~60°）。

### 19.2 扫描：`Services/LanScanner.cs`

判定分两步，避免把「端口开放」误当成水平仪：

1. **探测**：枚举本机所有 `Up` 且非 `Loopback` / `Tunnel` 网卡的 IPv4 地址，按 **/24** 展开 `1..254`（跳过本机自己的地址、跳过 `169.254.x.x` 这种没连上的 APIPA 地址），以 **128 并发 + 400ms 超时** 逐个 `TcpClient.ConnectAsync`；
2. **确认**：端口连得上不代表就是手机（可能被别的程序占着），所以再等最多 **600ms** 读一帧，用 `TiltReading.TryParse` 解析成功才标 `Confirmed = true`。手机端在客户端接入时会立刻补发最近一帧，正常情况下连上就能确认。

结果按「已确认在前 → IP 升序」排序。IP 排序是把四段拼成 `uint` 比较，不然字符串排序会出现 `192.168.1.10` 排在 `192.168.1.2` 前面。

### 19.3 输入框只填 IP

原来的 `ParseEndpoint`（要求 `host:port`）换成 `NormalizeHost`：截掉 `:` 之后的部分，端口一律用 `TiltNetClient.DefaultPort = 11223`。所以 `192.168.1.100` 与 `192.168.1.100:9999` 都是连到 `192.168.1.100:11223`。`ServerEndpoint` 属性随之改名 `ServerIp`，Watermark 与说明文案同步。

### 19.4 可用角度 0°~60°

`TiltGamepad` 去掉 `DeadZoneAngle`，`ToRatio` 变成 `min(|angle|, 60) / 60`：0° 居中、±60° 满舵、超出按满舵截断。原来的死区是为了让手机平放时的零点漂移不被当成转向；去掉后小幅晃动确实会产生一点点转向量，**需要游戏侧自己设方向盘死区**（多数赛车游戏都有）。

```kotlin
private fun bindGamepadButton(button: Button, onChanged: (Boolean) -> Unit) {

        false
    }
```

## 26. 两端打包

### 26.1 安卓：release APK

`app/build.gradle` 的 `release` 构建类型原来没有 `signingConfig`，直接 `assembleRelease` 只能得到 `app-release-unsigned.apk`（装不上）。项目里也没有任何 `.jks` / `.keystore`，所以给它加上：

```groovy
release {

    // 项目没有自己的签名文件：用 debug 签名给 release 包签名，
    // 这样打出来的 apk 可以直接覆盖安装已有的调试版（两者签名一致）。
    // 以后要正式分发时，换成自己的 signingConfig 即可。
    signingConfig signingConfigs.debug
    proguardFiles ...
}
```

## 30. LT / RT 改矩形操控框 + 手柄震动回传手机

需求两条：

1. LT / RT 从竖向滑动条换成**矩形框**，整个矩形就是操控（命中）面积，触控后**按百分比变色**；
2. 电脑端虚拟手柄收到的游戏震动**回传给手机**，手机跟着振。

### 30.1 安卓：`TriggerPadView`（新文件）替掉 `VerticalSeekBar`

`VerticalSeekBar.kt` 已删除，新增 [TriggerPadView.kt](../app/src/main/java/com/savitor/mobilewheel/TriggerPadView.kt)，自绘而非改造 SeekBar：SeekBar 既有自己的 drawable 和命中逻辑，要去掉滑块、让整块面积参与命中、还要按百分比染色，绕开它反而更省事。

| 项 | 实现 |
| --- | --- |
| 命中面积 | 整个 View（`onTouchEvent` 一律返回 true），`layout_width=match_parent`、`height=0dp + weight=4` |
| 取值 | `ratio = 1 - event.y / height`，顶部 = 满值，`progress = ratio * 255` |
| 按下即响应 | `ACTION_DOWN` 里就 `applyTouchY()`，不用等 `ACTION_MOVE` |
| 变色 | 从底部往上填充圆角矩形，颜色按比例三段插值：绿 `#66BB6A` → 黄 `#FFCA28` → 红 `#EF5350`（浅色系，黑字和边框仍看得清） |
| 松手回弹 | `ValueAnimator` 120ms 回 0，模拟扳机弹簧；`ACTION_CANCEL` / `onDetachedFromWindow` 也会停掉动画 |
| 圆角 | `min(cornerRadius, min(填充高度/2, 宽/2))`，填充块矮的时候自动收圆角，不然会凸出框外 |

`activity_main.xml` 里 `seekLt` / `seekRt` → `padLt` / `padRt`（`max` / `progressDrawable` 属性一并去掉，`max` 变成类里的默认值 255）。`MainActivity` 里 `triggerListener(label)` 换成 `bindTrigger(pad, label)`，`sendTilt()` 改读 `padLt.progress` / `padRt.progress`。

### 30.2 安卓：接收震动并播放

`TiltNetServer` 原来只写不读，现在同一条 socket 也读：`ClientWriter` 里起一个守护线程跑 `readLoop()`，按行读 JSON，`onRumbleReceived` 回调前切回主线程。

`MainActivity`：

| 项 | 实现 |
| --- | --- |
| 幅度 | 手机只有一个马达，取 `max(large, small)` |
| 播放 | 每 80ms 下一次 `VibrationEffect.createOneShot(80, 幅度)`，自己重排下一次 —— 强度变化最多 80ms 生效，不用维护长震动的取消逻辑 |
| 停振 | 收到 0 停；另外 >400ms 没收到新帧也停（**掉线 / 游戏停止震动的兜底**，省得电脑端还要专门发一次 0） |
| 权限 | `AndroidManifest.xml` 加 `android.permission.VIBRATE` |

### 30.3 Windows：把 `FeedbackReceived` 转发出去

| 文件 | 改动 |
| --- | --- |
| `TiltGamepad.cs` | 新增 `event EventHandler<(byte Large, byte Small)>? FeedbackReceived`；`Connect()` 里 `_pad.Connect()` 之后 `_pad.FeedbackReceived += OnPadFeedback`（**必须先订阅**，ViGEmBus 才会把游戏的输出报告回传），`ReleaseInternal()` 里解绑 |

### 30.6 踩到的坑

1. **震动被系统静音：`VibrationEffect.createOneShot()` 默认是 `USAGE_TOUCH`**。本机「触感反馈」是关的（`settings get system haptic_feedback_enabled` = 0，`dumpsys vibrator_manager` 里 `TOUCH = OFF`），于是 `dumpsys` 里每条振动都是 `status = ignored_for_settings`、`duration: 0ms` —— 请求发出去了但**根本不会振**。手柄震动不该跟随「触感反馈」开关，所以显式声明用法：

   ```kotlin
   val effect = VibrationEffect.createOneShot(RUMBLE_TICK_MS, rumbleAmplitude)
   if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.S) {
       // 必须显式声明 MEDIA：默认的 TOUCH 用法会跟随系统的“触感反馈”开关
       vibrator?.vibrate(effect, VibrationAttributes.createForUsage(VibrationAttributes.USAGE_MEDIA))
   } else {
       vibrator?.vibrate(effect)
   }
   ```

   改完 `status` 从 `ignored_for_settings` 变成 `cancelled_superseded` / `cancelled_by_user`（下一个一次性震动顶掉上一个、以及收尾时主动 `cancel()`，都是正常状态），`start` / `end` 时间戳也真的有了。`VibrationAttributes` 是 API 31 的，`minSdk` 是 26，所以加了版本判断。
2. **`IXbox360Controller` 上没有 `Dispose`**：`ViGEmClient` 才有，临时验证程序里写 `pad.Dispose()` 直接编译不过。
3. `adb shell input swipe x y x y 4000` 想「按住不放」是不行的：整条命令阻塞到抬手才返回，等它跑完再 `uiautomator dump` 读到的还是 0。要用 `input motionevent DOWN x y` / `UP x y` 两条命令分开注入，中间再 dump。
4. Android 12+ 起 `dumpsys vibrator` 换成了 `dumpsys vibrator_manager`，且「Recent vibrations」是**按 usage 分组**列出的，不看全量输出容易以为自己的振动没记录（本轮的 `TOUCH` 和 `MEDIA` 就是分在两个组里）。
